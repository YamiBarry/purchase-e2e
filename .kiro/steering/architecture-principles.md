# 架构决策原则

## 1. 前后端职责边界

**判断标准：如果"是否展示/是否生效"涉及以下条件的组合，决策必须归后端：**

- 用户身份/状态（首单、会员、黑名单）
- 时间窗口（有效期、冷却期、活动时间）
- 实验分组（AB 实验）
- 业务规则（满减门槛、使用次数、互斥关系）

**前端职责**：拿到 `shouldShow=true` 就渲染，`false` 就不渲染。职责仅为展示 + 埋点 + 交互。

**自检**：如果产品明天加一个条件，前端需要改代码吗？如果需要，说明职责划分错了。

## 2. 接口设计规范

### 命名
- RESTful 风格：`GET /ec-{service}/{resource}` 查询，`POST /ec-{service}/{resource}` 创建/操作
- 聚合接口：`GET /ec-{service}/{page}/context` 返回页面所需的全部数据（含展示决策）

### 请求/响应结构
```
// 统一响应
{
  "code": 200,          // 业务状态码
  "message": "success",
  "body": { ... }       // 业务数据
}
```

### 错误码
- 200：成功
- 400：参数错误
- 401：未登录
- 403：无权限
- 500：服务端异常
- 业务错误码：6 位数字（如 100001），定义在 `*MessageCode.java`

## 3. 跨服务通信决策

| 场景 | 选择 | 原因 |
|------|------|------|
| 需要实时结果 | Feign 同步调用 | 调用方需要返回值继续处理 |
| 可异步、允许延迟 | RabbitMQ | 解耦、削峰、重试 |
| 查询类、高频 | Redis 缓存 + Feign 兜底 | 减少跨服务调用 |

## 4. 数据聚合层

**何时需要 BFF/聚合接口：**
- 前端一个页面需要调用 3+ 个后端服务的数据
- 前端需要组合多个条件做展示决策（应收归后端）
- 需要减少前端请求数量

**当前项目模式：**
- ec-prebff：聚合层（如果已有）
- 各 ec-*-service 直接提供页面级接口（更常见）

## 5. 新增接口 vs 复用已有接口

**判断流程：**
1. 搜索是否已有满足需求的接口（含字段）
2. 已有但缺字段 → 在已有接口上扩展（加字段），不新建
3. 完全没有 → 新建接口，遵循上述命名规范
4. 已有但职责不匹配（如把营销字段塞进订单接口）→ 新建独立接口
