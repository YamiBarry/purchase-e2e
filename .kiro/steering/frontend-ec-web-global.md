# Web 前端通用开发规范

## 1. 使用方式
- 必须先确定当前项目是否为 web 前端项目；若不是，本规范不适用。
- 项目专属规则由各项目的 steering 文件自动加载，本文件仅包含所有项目通用的规则。

### 术语与冲突处理
- 规则动词：`必须`=硬约束，`禁止`=绝对不要，`优先`=默认策略。
- 冲突处理：项目规则 > 通用规则。

## 2. 通用规则（所有项目）
### 2.1 基础协作约束
- 必须兼容优先、最小改动优先，不主动做主版本升级或大重构。
- 必须先定位入口、数据流、构建链路，再开始修改。
- 必须复用现有目录与模块，不平行新建同类体系。
- 必须只修改任务相关文件，避免无关变更。
- 必须保护敏感信息，禁止在代码/配置/日志中暴露密钥、token、密码、内部地址等。
- 必须避免在前端长期存储敏感凭据到 `localStorage`/`sessionStorage`，优先 httpOnly Cookie 或后端会话。
- 必须使用项目已有脚本和校验流程，不自创新构建流程。
- 必须在交付说明中写清：改动文件、影响范围、验证结果、剩余风险。

### 2.2 前端最佳实践模式（优先）
- 优先采用"页面编排层 + 业务层 + 数据访问层 + 展示组件层"的分层结构。
- 优先让 UI 组件保持无副作用，业务逻辑下沉到 service/store/hook。
- 必须做到单向数据流：输入明确、输出明确，避免隐式全局状态耦合。
- 必须统一请求入口、统一错误处理、统一 loading/empty/error 状态表达。
- 必须把接口字段映射为业务可读结构，禁止把后端原始结构直接散落到 UI。
- 必须把常量集中管理（路由名、事件名、接口地址、magic number）。
- 优先写小组件和小函数，单文件过大时主动拆分。
- 必须处理边界条件：空数据、超时、重试、异常回退与兜底 UI。
- 必须保持可访问性基础：语义化标签、可聚焦交互、必要 ARIA。
- 必须保持可维护样式策略：限制全局样式污染，组件样式就地收敛。
- 必须把文案国际化与配置化，禁止在业务代码中散落硬编码文案。
- 必须先保证正确性，再做性能优化；优化必须有明确目标与验证依据。

### 2.3 通用反模式（禁止）
- 禁止"巨石组件"：一个文件同时承担请求、状态、渲染、埋点、路由控制。
- 禁止复制粘贴同类逻辑到多个页面，不抽公共层。
- 禁止绕过项目既有请求封装、路由机制、状态管理约定。
- 禁止使用非语义标签充当交互控件（如 `div/span` 代替 `button/a`）。
- 禁止 UI 展示组件直接发起接口请求，数据获取必须经上层或数据层。
- 禁止向 `v-html` / `dangerouslySetInnerHTML` 注入不可信 HTML 字符串。
- 禁止在公共入口一次性引入整包大型库（如 `import _ from 'lodash'`），必须按需引入。
- 禁止使用 `eval`、`new Function` 或动态注入 `<script>` 执行字符串代码。
- 禁止硬编码环境域名、业务链接、埋点事件、语言文案。
- 禁止 silent fail：吞掉异常、不打日志、不返回可诊断信息。
- 禁止关闭或大范围禁用 ESLint/Prettier；特殊情况仅允许最小范围并注明原因。
- 禁止为赶进度跳过 lint/typecheck 后直接交付。

## 3. 通用交付要求
- 必须先给结论，再给改动细节。
- 必须列出已执行验证命令与结果摘要。
- 必须标注未执行项与原因（如环境限制）。
- 优先给出下一步可选动作（补测、回归、拆分提交）。
